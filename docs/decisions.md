# Решения (ADR)

Короткие записи о том, почему сделано именно так. Формат: контекст → решение →
следствия. Новые решения добавляются сверху, старые не переписываются.

---

## ADR-10. Стек: React + TypeScript + Vite, без переезда на vanilla

**Контекст.** Есть две реализации: эта (React 19 + TS + Vite/CRXJS) и переписанная
вручную на vanilla JS (3.0). Vanilla-версия компактнее по строкам, но именно она
потеряла три свойства React-версии: перестановку через dnd-kit, сохранение
фокуса/скролла и `tabs`-независимую проверку URL.

**Решение.** Продукт развивается в этом репозитории на React + TS. Фичи 3.0
(приоритеты, фильтры, поиск, экспорт/импорт, компактный режим) перенесены сюда.

**Следствия.** Есть сборка, типы и юнит-тесты; цена — ~60 КБ gzip на React.
Для панели, которая живёт открытой, это приемлемо.

## ADR-09. Единственный ключ сортировки — `order`

**Контекст.** В 3.0 сортировка была `(priority desc, order asc)`, а перестановка
писала только `order`. Итог: перетаскивание задачи с высоким приоритетом ниже
обычных **молча не работало** — замерено в браузере.

**Решение.** Список сортируется только по `order`. Приоритет — визуальный атрибут
(`data-priority`, бейдж «важно»), на порядок не влияет.

**Следствия.** Drag&drop всегда работает. Если понадобится «сначала важные» — это
будет отдельная команда, которая пересчитывает `order`, а не второй ключ
сортировки.

## ADR-08. Хранилище: `chrome.storage.local` + миграция из 1.x и 3.0

**Контекст.** 1.x держала задачи в `localStorage` (при объявленном разрешении
`storage`), 3.0 — в `chrome.storage.local` под ключом `tasks_v3`. У пользователя,
обновившего расширение, список просто исчезал.

**Решение.** Актуальный ключ — `tasks` (схема 4, `schemaVersion`). При первом
запуске `loadState()` читает `tasks_v3` и `localStorage.tasks`, объединяет по `id`
и по паре «текст + createdAt», пишет результат, сохраняет сырую копию в
`legacyBackup` и очищает `localStorage`. Ключ `tasks_v3` не удаляется.

**Следствия.** Обновление не теряет данные, откат к 3.0 остаётся возможным.
Идемпотентность обеспечена `schemaVersion`, миграция покрыта юнит-тестами и e2e.

## ADR-07. Состояние панели: события `onOpened/onClosed` + переподключение порта

**Контекст.** В 1.x/3.0 состояние жило в `Set` внутри service worker и терялось при
его выгрузке: popup показывал «Открыть», когда панель была открыта.

**Решение.** Источник истины — `sidePanel.onOpened/onClosed` (Chrome 141+).
Страница панели держит порт, шлёт `panel:hello` со своим `windowId` и при обрыве
переподключается через 1 с — это восстанавливает состояние после перезапуска SW.
На Chrome < 141 порт остаётся единственным источником.

**Следствия.** SW не открывает панель сам (жест не передаётся через сообщение):
`open()`/`close()` вызываются из popup и из обработчика `chrome.commands.onCommand`.

## ADR-06. `minimum_chrome_version: "116"` + рантайм-детект

**Решение.** Минимум — Chrome 116 (`sidePanel.open()`). Всё, что новее (`close`,
`onOpened/onClosed`, `getLayout`), проверяется через `typeof`; для закрытия есть
fallback через `setOptions`.

**Следствия.** Шире охват; цена — ветка кода, которая на новых версиях не
исполняется (и поэтому помечена как непроверенная в `docs/knowledge-base.md`).

## ADR-05. Минимальные разрешения: только `sidePanel` и `storage`

**Контекст.** 1.x просила `tabs` (ради `tab.url`), 3.0 заменила на `activeTab` и
продолжала просить несуществующее `commands`.

**Решение.** Разрешений два. Вместо проверки URL — обработка отказа `open()` с
человеческим сообщением.

**Следствия.** Ни одного предупреждения о данных при установке. Проверка того,
что панель недоступна на системной странице, опирается на текст ошибки Chrome —
если он изменится, пользователь увидит общее «Не удалось открыть панель»
(тест `describeOpenError` фиксирует известные формулировки).

## ADR-04. Локализация через `_locales`, два языка (ru + en)

**Решение.** Все строки — в `public/_locales/{ru,en}/messages.json`; манифест
использует `__MSG_extName__`, `default_locale: "ru"`. В коде — `t(key)` поверх
`chrome.i18n.getMessage`.

**Следствия.** `npm run validate` проверяет: одинаковый набор ключей, согласованное
число подстановок `$n`, корректную форму записей, отсутствие ключей, которых нет в
коде. `npm run load-test` прогоняет панель и popup на двух языках.

## ADR-03. Drag&drop: dnd-kit, ручка вместо всей карточки

**Решение.** `PointerSensor` (порог 5 px) + `KeyboardSensor` (пробел + стрелки),
`listeners` только на ручке, `SortableContext` по видимому списку. Перестановка
внутри фильтра пишется так, что позиции скрытых задач не двигаются
(`reorderVisible`).

**Следствия.** Текст задачи можно выделять мышью, перестановка работает с
клавиатуры и на тач-устройствах, drag не ломает приоритеты и фильтры.

## ADR-02. Отмена вместо подтверждения для обратимых действий

**Решение.** Удаление спрашивает подтверждение (необратимо с точки зрения UI), а
«убрать выполненные» и импорт — нет: вместо этого показывается уведомление с
«Отменить» (снимок списка в `useRef`).

**Следствия.** Меньше модальных окон, но нужен корректный снимок: колбэк из
уведомления создаётся в том же тике, что и `setState`, поэтому снимок хранится в
`ref` (иначе «Отменить» ничего не делала — поймано в e2e).

## ADR-01. Лимиты как продуктовое ограничение

`MAX_TEXT = 500` символов, `MAX_TASKS = 2000`. Импорт сверх лимита не обрезается
молча: в уведомлении пишется, сколько пропущено. Полный список пишется в storage
целиком — при таких лимитах это десятки килобайт.
