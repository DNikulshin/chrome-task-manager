# База знаний: боковая панель Chrome MV3 и наш опыт

Документ собирает факты, полученные при разработке этого расширения и при разборе
предыдущих версий (React 1.x на `localStorage` и vanilla-JS 3.0). Каждый пункт
помечен тем, **как он проверен** — «документация» это или измерение на стенде.
Непроверенное вынесено в конец отдельным разделом.

Стенд: Chrome for Testing **158.0.8127.37**, Linux, `--headless=new`, расширение
загружено распакованным (`--load-extension`).

---

## 1. API `chrome.sidePanel`: что и с какой версии

| API | С версии | Что даёт |
| --- | --- | --- |
| `setOptions({tabId, path, enabled})` | 114 | Включить/выключить панель для вкладки, подменить содержимое |
| `setPanelBehavior({openPanelOnActionClick})` | 116 | Клик по иконке сразу открывает панель (без popup) |
| `open({tabId, windowId})` | 116 | Открыть панель. **Требует user gesture** |
| `getOptions({tabId})` | 114 | Текущие опции панели |
| `getLayout()` | 140 | На какой стороне окна панель |
| `close({tabId, windowId})` | 141 | Программное закрытие |
| `onOpened` / `onClosed` | 141 / 142 | События открытия и закрытия с `windowId` |

Особенности `close()` (сверено с официальной документацией API):

- `close({windowId})` закрывает **глобальную** панель в окне — это наш случай
  (панель объявлена через `side_panel.default_path`, без per-tab настроек).
- `close({tabId})` ведёт себя по-разному: если открыта только глобальная панель,
  в Chrome 145+ промис отклоняется с ошибкой, а в 141–144 закрывалась глобальная.
  Поэтому `tabId` в `close()` лучше не использовать без нужды.
- До Chrome 141 программного закрытия не было вообще. Fallback, который мы
  держим: `setOptions({tabId, enabled:false})` + сразу `enabled:true` — панель
  исчезает, но остаётся доступной для следующего открытия.

**Как проверено:** `Object.keys(chrome.sidePanel)` на Chrome 158 →
`Side, close, getLayout, getOptions, getPanelBehavior, onClosed, onOpened, open,
setOptions, setPanelBehavior`; версии — из официальной документации.

Практический вывод: наш `minimum_chrome_version` — **116** (`open()`), а всё, что
новее, определяется в рантайме (`typeof chrome.sidePanel.close === "function"`).
Ставить минимум 141 было бы проще, но отсекло бы часть пользователей.

## 2. Разрешения: чего действительно не нужно

| Разрешение | Нужно? | Почему |
| --- | --- | --- |
| `sidePanel` | да | Без него `side_panel` в манифесте игнорируется |
| `storage` | да | `chrome.storage.local` |
| `tabs` | **нет** | `chrome.tabs.query()` возвращает `id` и `windowId` без разрешения |
| `activeTab` | нет | Даёт `tab.url`, но только на время гранта (клик по иконке/команда) |
| `commands` | **нет** | `commands` — это ключ манифеста, а не разрешение; в официальном списке разрешений его нет |
| `clipboardWrite` | нет | Запись в буфер из сфокусированного документа панели разрешена |

Замер: на свежем профиле без user gesture `chrome.tabs.query({active:true})`
возвращает `{ id: ..., windowId: ..., url: null }`. То есть попытка отсечь
`chrome://` по `tab.url` **не работает**, если нет `tabs` или живого гранта
`activeTab`. Правильнее не смотреть на URL вообще, а ловить отказ `open()`:

```ts
try { await chrome.sidePanel.open({ tabId }); }
catch { /* системная страница или нет жеста */ }
```

Так расширение не просит лишних разрешений — в Web Store у него нет ни одного
предупреждения о данных.

## 3. Язык интерфейса в headless: `--lang` не решает

Самое неочевидное место. Проверено в трёх вариантах на Chrome 158 (Linux):

| Способ | `chrome.i18n.getUILanguage()` | `getMessage("appTitle")` |
| --- | --- | --- |
| `--lang=ru` + `intl.app_locale:"ru"` в `Default/Preferences` | `en-US` | `Tasks` (английский) |
| `--lang=de` (локаль, которой у расширения нет) | `en-US` | `Tasks` |
| `LANGUAGE=ru` / `LANG=ru_RU.utf8` в окружении процесса | `ru` | `Задачи` |

Вывод: локаль расширения берётся из **окружения процесса**, а не из флага
`--lang` (он меняет только `navigator.language`) и не из `intl.app_locale`
(Chrome 158 его игнорирует в headless). Для проверок в `scripts/cdp.mjs` мы
задаём `LANGUAGE`, `LANG`, `LC_ALL` и дополнительно пишем `app_locale` в профиль —
на случай, если поведение вернётся.

Мораль для тестов: судить о локали только по `getMessage()`, а не по
`getUILanguage()` и не по `navigator.language`.

## 4. Состояние боковой панели не живёт в service worker

`chrome.sidePanel` не умеет отвечать «открыта ли панель сейчас» (до 141 такого
API не было вовсе). Классический обход — порт из страницы панели:

```ts
// service worker
chrome.runtime.onConnect.addListener((port) => {
  if (port.name !== "sidepanel") return;
  openWindows.add(windowId);       // ← откуда windowId?
  port.onDisconnect.addListener(() => openWindows.delete(windowId));
});
```

Проблема: у порта из страницы панели **нет `sender.tab`**, поэтому `windowId`
неизвестен. Второе: service worker выгружается при простое, и вместе с ним
пропадает порт и весь накопленный `Set`. Замер на версии 3.0: после
`ServiceWorker.stopAllWorkers` запрос `GET_PANEL_STATUS` возвращал
`{ isOpen: false }`, хотя панель была открыта — popup начинал показывать
«Открыть».

Решение в 4.0:

1. Источник истины — события `sidePanel.onOpened/onClosed` (Chrome 141+), они дают
   `windowId` и не зависят от порта.
2. Порт остаётся как fallback для Chrome < 141 и как «лечение» после перезапуска
   SW: страница панели при подключении присылает `{ type: "panel:hello", windowId }`
   (`chrome.windows.getCurrent()` работает без разрешений), а при обрыве порта
   **переподключается через 1 с**.
3. Состояние — `Set<number>` окон, переходы описаны чистой функцией
   `applyPanelEvent` (`src/lib/panel.ts`), покрытой юнит-тестами.

Проверка: `npm run load-test` останавливает все service worker'ы и убеждается, что
через 2 секунды окно снова помечено открытым.

## 5. `chrome.storage.local` в деталях

- **`onChanged` не срабатывает на запись того же значения.** Проверено: запись
  идентичного массива задач не вызывала перерисовку в 3.0. Поэтому «своё эхо»
  фильтруется по сериализованному снимку, а не по флагу «я сейчас пишу».
- **Пишем всегда весь список.** Частичные записи (`tasks[id]`) дают гонки: два
  быстрых действия читают старое состояние и перетирают друг друга.
- **Порядок событий соответствует порядку записей**, но обработчик может
  получить устаревший снимок, если в этот момент уже есть более новый. Отсюда
  правило: снимок, который записали мы сами, в состояние не применяем.
- `localStorage` в странице расширения живёт на origin `chrome-extension://<id>`.
  Он переживает перезапуск браузера, но не виден service worker'у и теряется при
  удалении данных сайтов. Для продукта — только `chrome.storage`.

## 6. Дефекты версии 3.0, которые стоили данных и времени

Найдены и измерены при ревью vanilla-версии (17 проверок в реальном Chrome).
Все закрыты в 4.0 и сторожатся автотестами.

| Дефект | Замер | Как закрыт сейчас | Кто сторожит |
| --- | --- | --- | --- |
| Новый `document.addEventListener("click")` на каждый `render()` | 12 слушателей за 8 рендеров | Слушатель ставится только пока меню открыто, с `cleanup` | `e2e`: «слушатели document не накапливаются» |
| `onChanged` → полный `render()` | черновик в поле ввода исчезал | React не пересобирает DOM; своё эхо фильтруется | `e2e`: «черновик не потерялся» |
| Сортировка по `(priority, order)`, перестановка по `order` | drag high-задачи вниз — no-op | Единственный ключ `order`, приоритет — только вид | `e2e`: «перетаскивание high-задачи вниз» |
| Состояние панели в памяти SW | после перезапуска SW `isOpen:false` | События + переподключение порта | `load-test`: «после перезапуска SW…» |
| Полная пересборка DOM на действие | `scrollTop 400 → 0`, фокус уезжал в `body` | Точечные обновления React | `e2e`: «позиция скролла сохранилась» |
| Нет миграции данных | задачи 1.x/3.0 исчезали при обновлении | `loadState()` переносит оба старых формата | `storage.test.ts`, `e2e`: «миграция v3 + v1» |
| Импорт валил всю пачку из-за одной записи | `{text:123}` → «Ошибка чтения файла», 0 задач | Поэлементная валидация + счётчик пропущенных | `tasks.test.ts`, `e2e`: «импорт заменил список» |
| Нет подтверждения при импорте | список заменялся молча | Диалог с количеством + undo | `e2e`: «импорт спрашивает подтверждение» |

## 7. Ловушки инструментов (сэкономят полдня)

1. **Branded Chrome игнорирует `--load-extension` с версии 137.** Нужен Chrome for
   Testing / Chromium.
2. **CDP не видит `chrome.*` в контексте service worker.** `typeof chrome` внутри
   `Runtime.evaluate`, привязанного к SW-таргету, возвращает `undefined` — и через
   прямой websocket, и через `Target.attachToTarget`. Поэтому все проверки
   расширения делаются из **страницы расширения**, а SW проверяется сообщением
   (`panel:get-state`).
3. **Enter через CDP.** `Input.dispatchKeyEvent` с `type: "rawKeyDown"` не вызывает
   действие по умолчанию (submit формы). Нужно `type: "keyDown"` + `text: "\r"`.
   Пробел — `type: "keyDown"`, `text: " "`, `code: "Space"`.
4. **dnd-kit + PointerSensor** включается после `activationConstraint.distance`
   (у нас 5 px): «нажать и отпустить» без движения не начнёт drag. В e2e движение
   эмулируется 8 шагами по 40 мс.
5. **Липкая шапка перекрывает карточки.** Клик по координатам карточки, ушедшей
   под шапку при `scrollTop > 0`, попадает в шапку. В тестах берём первую
   карточку, чей `top` ниже границы `.panel-top`.
6. **Невалидный `messages.json` = молчаливая неработа расширения.** Chrome не
   грузит расширение и не пишет причину в stderr; помогает
   `chrome --pack-extension=dist --no-sandbox`, который печатает
   `Not a valid tree for key <key>` (мы один раз записали ключ строкой вместо
   `{ "message": ... }`). Теперь это проверяет `npm run validate`.
7. `Intl.RelativeTimeFormat` со `style: "narrow"` в русской локали даёт `-2 мин`
   без «назад». Для человеческих дат нужен `style: "short"`.

## 8. Что осталось непроверенным

- **Открытие панели настоящим user gesture.** В headless жест не воспроизвести:
  `sidePanel.open()` проверяется только по коду ошибки. Ручной чек-лист — в
  `docs/testing.md`.
- **Fallback закрытия на Chrome < 141** (`setOptions({enabled:false})`): код есть,
  но на стенде Chrome 158 всегда доступен `close()`.
- **Квоты `chrome.storage.local`.** Лимит 10 МБ, у нас ограничение 2000 задач ×
  500 символов, но поведение при исчерпании (текст ошибки) проверено только
  модульным тестом-заглушкой, не реальным переполнением.
- **Ревью Chrome Web Store**: политика по `storage` и описанию — прогноз, не факт.
